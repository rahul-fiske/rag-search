# Critical architecture review (rag-search 0.7.8)

> Status (0.8.0): the ten "top recommended actions" below were implemented in 0.8.0, together
> with the RAG_SEARCH_THREADS fix; the remaining lower-priority findings are still open -- see the
> status section of `enhancement-plan.md`. File:line references below are to 0.7.8.

## Scope and method

Requested 2026-10-02: "a very critical and thorough analysis of current code architecture, evaluate for redundancy, efficiency, correctness, accuracy of indexing/search/models. Recommend changes/improvements/rewrite." Four subsystems were each reviewed in full by an independent pass (every file in scope read completely, not sampled), cross-checking call sites across subsystem boundaries where relevant: (1) indexing/conversion, (2) search/retrieval, (3) models/embedding, (4) storage/access/API/CLI/MCP. 37 findings total, file:line-cited, each rated for severity and given an explicit fix-scope recommendation (targeted fix / localized refactor / rewrite).

## Overall verdict: improve, don't rewrite

None of the four passes surfaced a structural flaw that calls the architecture itself into question — the layering (api.py as the single shared entry point; CLI/MCP/UI as thin adapters; daemons for warm model state; atomic-write-then-symlink-swap for publish generations; per-document index dirs merged per-collection) holds up, and several "is this designed right" checks came back clean (RRF math, cosine-similarity consistency, BM25 IDF smoothing, the MCP adapter's layering discipline, publish.py's atomicity). What the review found instead is a consistent pattern: **individual pieces of correct design that a later addition didn't fully extend to** — a cache or lock pattern built once (`AccessStore`, `write_json_atomic`) and not reused by the next metadata store that needed the same thing (`descriptions.json`); a tunable registry (`spec.py`) that one backend (`Qwen3Reranker`) wires up correctly and a sibling backend (`Reranker`, the actual default) doesn't; a case-folding convention applied in three places and missed in a fourth that happens to sit on the live search path. This is exactly the shape of problem targeted fixes and localized refactors resolve well, and a rewrite would not — a rewrite would just risk reintroducing the same class of drift from scratch. Recommendation: work the priority list below as targeted fixes/refactors, and treat the recurring pattern itself (new addition doesn't reuse the existing shared helper for caching/locking/env-wiring) as something to check for explicitly in review from now on, including for the upcoming flexible-docs-location/export-import work, which will add at least one more such store (the collection-location registry) and should be built *reusing* `AccessStore`'s pattern from day one rather than adding a fifth copy of it.

## Highest-priority findings across all four subsystems

Ranked by a combination of severity and reach (how many call paths/surfaces are affected), not by subsystem:

1. **Access-control case mismatch on the live search path** — `policy.resolve_scope` (`policy.py:83-98`) compares requested collection names case-sensitively while every other part of the codebase (`Rules.allows`, `access._canonical`, `descriptions._canonical`) case-folds. Called directly from `core/search_daemon.py:261`, so every `search`/`grep` request with a differently-cased but authorized collection name gets a false "unknown collection." [storage/access layer, finding 1]
2. **Same-stem single-file indexing silently overwrites a different document's index** — `index_dir_for`/`markup_path_for` (`paths.py:316-323`) key off `rel.stem`, discarding the extension; the collision guard in `run_index` only checks within one call's batch, and `worker.resolve_sources` returns a one-element list for single-file jobs, so indexing `report.docx` after `report.pdf` (same folder/stem) silently deletes `report.pdf`'s index with no error. [indexing pipeline, finding 1]
3. **RRF double-counting via duplicate collection names in a request** — `search()`'s `wanted` list (`search.py:269-270`) is never deduplicated, and nothing upstream (`parse_collections`, `resolve_scope`) dedupes either; a client-supplied `collections: "hr,hr"` silently doubles that collection's fused-ranking weight. Reachable through ordinary request input on any surface (MCP tool, dashboard, CLI). [search pipeline, finding 1]
4. **The default reranker silently ignores its own documented tunables** — `Reranker.score()` (`core/embedding.py:220-231,242`) hardcodes batch size and max length instead of reading `RAG_SEARCH_RERANK_BATCH`/`RAG_SEARCH_RERANK_MAX_LEN`, even though `spec.py` advertises both and the sibling `Qwen3Reranker` backend honors them correctly. A user tuning these for the model everyone actually runs by default sees no effect and no error. [models layer, finding 1]
5. **No offline-first model loading, in a tool explicitly built for network-blocked environments** — nothing sets `HF_HUB_OFFLINE`/`local_files_only=True`; a cold daemon boot with an already-cached model can still hang/retry on a blocked Hub metadata call, and `explain_download_error`'s friendly error translation is wired only into the explicit download-task path, not into the `Embedder.load()`/`Reranker.load()` paths the daemon/indexer/playground actually hit at startup. [models layer, finding 2]
6. **The whole search pipeline is serialized behind one global lock in the search daemon** — `_search()` (`core/search_daemon.py:323-328`) holds the lock around BM25 + dense + fusion + reranking for the full request duration, even though `Generation`/`IndexData` are documented as immutable and safe to read concurrently; one slow query (many collections, large rerank pool) head-of-line-blocks every other concurrent client on a daemon whose per-connection-thread design clearly intends to serve them concurrently. [search pipeline, finding 5]
7. **No locking around the read-modify-write cycle on `access.json`/`descriptions.json`** — the final write is atomic, but two concurrent CLI invocations each reading-then-writing the same file can silently lose one's update. Gets materially worse with the planned export/import and multi-location registry, which will add more such stores under the same pattern unless fixed first. [storage/access layer, finding 5]
8. **Deleted-source cleanup doesn't happen in normal operation** (previously confirmed while drafting the flexible-docs-location plan update, restated here for completeness since it's squarely "correctness of indexing/accuracy of the index" in scope): `merge_collection()` excludes a deleted document from the merged `_all/` index but never deletes its per-doc index dir/markup file; actual deletion only happens via `_wipe()`, gated behind `index all`/`--wipe`, which wipes-and-rebuilds the *current* scan rather than targeting what's missing. Orphaned per-doc artifacts accumulate on disk indefinitely. See `flexible-docs-location-analysis.md` §1 for the full writeup and recommended fix (incremental `index new` should compute and reclaim the dead set, not just exclude it from the merge).
9. **Legacy-torch-load safety gate leaks process-wide** — the CVE-2025-32434 workaround (`core/embedding.py:114-140`) monkey-patches a transformers safety check off globally and permanently once any trusted (`BAAI/*`) model loads first in a long-lived daemon, so the check stays disabled even for a later, untrusted, user-chosen model in the same process. [models layer, finding 3]
10. **BM25 document-length normalization is biased by compound-token duplication** — `tokenize()` (`core/bm25.py:17-26`) appends both a hyphenated/compound token and its split parts to the same token list, which `BM25.__init__` then also uses to compute document length for the `b`-normalization term, making compound-heavy chunks (IDs, versions, file paths) score as artificially longer and therefore unfairly discounted relative to equivalent-content chunks without compounds. [search pipeline, finding 4]

## Subsystem 1: Indexing / conversion pipeline

Files: `core/indexer.py`, `core/chunker.py`, `core/docling_convert.py`, `core/legacy_convert.py`, `core/worker.py`, `core/indexer_daemon.py`, `core/daemon_base.py`, `publish.py`, `jobs.py`.

- **[HIGH]** Same-stem collision silently overwrites a different document's index on single-file indexing jobs (`paths.py:316-323`, `worker.py:83-86`, `indexer.py:513-524`) — see priority finding #2 above. Fix: key the index directory by the full filename, not just the stem, or re-check collisions against *all* existing per-doc dirs, not just the current batch.
- **[MEDIUM]** `RAG_SEARCH_THREADS` is set via `os.environ.setdefault(...)` (`indexer.py:577-578`), so in a long-lived process that calls `run_index` repeatedly (`playground.build_index`), only the first call's thread count ever takes effect; later builds with different job/doc counts inherit a stale value.
- **[MEDIUM]** `prepare_document` unconditionally hashes the full file (`indexer.py:226`) with no cheap mtime/size pre-filter, so "nothing changed" incremental runs scale with total corpus size, not the delta.
- **[MEDIUM]** No per-document wall-clock bound on the phase-1 conversion pool (`indexer.py:585`, `cf.as_completed` with no timeout); combined with docling's own timeout being best-effort/version-dependent and only reliably enforced when a separate `RAG_SEARCH_DOCLING_PYTHON` interpreter is configured (`docling_convert.py:340-344,427-437`; the only unconditional timeout, `indexer.py:171-178`, only fires in that non-default configuration), one pathological document can hang an entire run indefinitely with no automatic recovery.
- **[LOW-MEDIUM]** `merge_collection` reloads every document's `nodes.json`/`embeddings.npy` for the whole collection on any change (`indexer.py:378-392`), not just the changed document — bounded by the manifest-sha freshness skip, but cost per changed-collection merge grows linearly with collection size.
- **[MEDIUM]** Table-chunking loses the header row specifically on the "one enormous row" split branch (`chunker.py:67-71`), unlike the other two split branches, which correctly re-prepend it — an inconsistent, silent loss of retrieval context for that one case.
- **[MEDIUM]** `RAG_SEARCH_OCR` defaults to `"force"` (`docling_convert.py:53`), OCRing every PDF page even for clean born-digital PDFs where the docstring itself says `smart`/`auto` would be "much faster" — an expensive default most users indexing ordinary documents pay without realizing it.
- **[LOW]** `.doc`/`.xls`/`.ppt`/`.rtf` conversion is a separate manual `convert-legacy` step rather than an automatic pre-pass inside indexing when LibreOffice is available — a workflow gap, not a correctness bug; the conversion module itself is well-designed and defensive.
- **[MEDIUM]** Orphan-worker detection silently no-ops when `ps` is unavailable (`indexer_daemon.py:53-59,184-196`) — directly relevant to the containerization track, since slim/distroless images commonly lack `ps`; a missed orphan can race a new run on the same workspace. Recommend checking `/proc/<pid>/cmdline` directly on Linux instead of shelling out, or failing safe (assume still-running) rather than failing open.
- **[LOW]** `_cancel`'s 30s join can return before the worker process fully exits in rare cases, briefly confusing `already_running` state; self-correcting.
- `publish.py`/`jobs.py`: no issues found beyond the already-known deleted-source-cleanup gap (priority finding #8); the atomic symlink swap, generation rotation, and event-log replay/dedup logic are sound, and `jobs.py` keys correctly by literal filename (not the stem-derived path that causes finding #2), which is actually the right pattern finding #2 should be brought in line with.

## Subsystem 2: Search / retrieval pipeline

Files: `core/search.py`, `core/bm25.py`, `core/search_daemon.py`, `grep.py`.

- **[MEDIUM]** RRF double-counting from unde-duplicated collection scope — see priority finding #3.
- **[LOW]** BM25 index rebuild (tokenize + postings) happens from scratch on every reload of a changed collection (`search.py:49-54`) — bounded to actually-changed collections by the manifest-sha carry-over, but nothing persists pre-tokenized postings alongside `nodes.json`/`embeddings.npy`, so a large changed collection pays full Python-side retokenization on every daemon reload.
- **[LOW]** Pool-truncation tie-breaking is collection/stage-order dependent (stable sort over dict insertion order, `search.py:335`) rather than any secondary signal — minor, worth documenting if reproducibility matters.
- Positive findings worth keeping in mind for the "don't rewrite" verdict: dense similarity is correctly cosine (consistent `normalize_embeddings=True` on both index and query sides), query-vs-document embedding calls are correctly distinguished, RRF's rank-offset math is off-by-one-correct, `RRF_K=60` matches the literature default, and BM25's IDF smoothing uses the correct non-negative variant.
- **[LOW-MEDIUM]** BM25 tokenizer inflates document length via duplicated compound sub-tokens — see priority finding #10.
- **[MEDIUM-HIGH]** Search daemon serializes the entire query pipeline behind one lock — see priority finding #6.
- **[LOW]** Unbounded thread-per-connection in the daemon base (`daemon_base.py:189`) — low real-world severity for a local, few-client tool, worth a cap if usage grows.
- **[LOW]** `install(None)` (search_daemon.py:167-171) always discards the warm generation when nothing is published, with no guard distinguishing a genuine unpublish from a transient read hiccup — speculative hardening, no observed bug.
- **[MEDIUM]** `grep_isolated()` forks a fresh Python subprocess for every `rag_grep` call regardless of pattern risk (`grep.py:111-137`) — a sound safety rationale (regex backtracking holds the GIL) but paid on every call, including the overwhelming majority of benign patterns; worth gating subprocess isolation behind a cheap pattern-risk heuristic.
- **[LOW]** Files over 64MB are silently skipped by `grep_markup()` with no record in the result (`grep.py:70-72`) — a caller can get a confident "no matches" against a corpus that was partially unscanned.

## Subsystem 3: Models / embedding layer

Files: `core/embedding.py`, `models.py`, `model_tasks.py`, `spec.py`.

- **[HIGH]** Default reranker ignores `RAG_SEARCH_RERANK_BATCH`/`RAG_SEARCH_RERANK_MAX_LEN` — see priority finding #4.
- **[HIGH]** No offline-first model loading despite the network-blocked deployment target — see priority finding #5.
- **[MEDIUM/HIGH]** Legacy-torch-load safety patch leaks process-wide — see priority finding #9.
- **[MEDIUM]** Dtype defaults are asymmetric and undocumented across backends — `Embedder`/`Qwen3Reranker` default to half precision, `Reranker` explicitly defaults to full precision, and `spec.py`'s single `dtype` tunable description doesn't surface that the "automatic" choice is actually backend-dependent; switching reranker backends changes memory/quality characteristics the user never asked for.
- **[MEDIUM]** Silent over-length truncation risk concentrated on non-Latin text — `chunker.py`'s `est_tokens` heuristic (`chars/4` for non-whitespace-segmented scripts) can substantially undercount real subword-tokenizer output for CJK and similar languages that bge-m3 is explicitly marketed to support, so a chunk estimated safely under the 1024-token embed limit can still get silently truncated by sentence-transformers with no log line or metadata flag.
- **[MEDIUM]** `machine_info()`'s device/memory estimate (stdlib-only, used for dashboard fit-level warnings) diverges from the actual runtime device selection in `pick_device()` — on a Linux host with an NVIDIA GPU, the estimator assumes full fp32 CPU-class memory while the model will actually run on CUDA in fp16, potentially blocking a switch that would in fact fit comfortably. A defensible tradeoff for keeping `models.py` import-light, but worth surfacing in the warning text rather than silently mis-estimating.
- **[MEDIUM]** Model identity is not reproducible — every gate that mixes/re-uses embeddings (`config.json`, `index.meta.json`, `search.py`'s `ModelMismatch` check) keys purely off the Hugging Face repo id string with no recorded revision/commit SHA, so an upstream default-revision update (a legitimate HF workflow) can silently put different weights behind the same configured id with nothing in this codebase able to detect it. Directly relevant to the export/import work in `flexible-docs-location-analysis.md` §3, which currently also plans to gate only on model id — recommend both pieces of work record and (at least eventually) compare the resolved commit SHA, not just the id.
- **[LOW]** bge-m3's catalog entry advertises 8k-token inputs while the shipped default (`EMBED_MAX_SEQ=1024`) uses 1/8 of that window, with the gap not surfaced anywhere a user would see it before picking the model expecting long-chunk support.
- **[LOW, accepted as designed]** A model switch's verify step and its subsequent re-embed each load the candidate model once (two loads total) — real but modest redundancy, and the correct tradeoff given the deliberate process-isolation/crash-containment design documented in `worker.py`.
- `spec.py` itself is internally consistent (defaults, CLI flags, env names, validation all line up); the `rerank_batch`/`rerank_max_len` breakage is squarely a bug in `embedding.py` not honoring what the registry already declares correctly.

## Subsystem 4: Storage / access / API / CLI / MCP layer

Files: `paths.py`, `catalog.py`, `api.py`, `policy.py`, `access.py`, `descriptions.py`, `client.py`, `protocol.py`, `register.py`, `service.py`, the optional host module, `config.py`, `cli.py`, `mcp/server.py`, `mcp/profiles.py`, `ui/server.py`.

- **[HIGH]** `policy.resolve_scope` case-sensitive collection match on the live search path — see priority finding #1.
- **[MEDIUM]** `AccessStore`'s mtime-cache exists but `api.py` never uses it — `describe_collection`, `local_grep`, and `index_status` all call raw `load_rules()` instead (twice, in `index_status`'s case), re-reading and re-parsing `access.json` on every call from what's meant to be a cache-fronted store, including from the long-lived MCP adapter and the dashboard's 1 Hz poll loop.
- **[MEDIUM]** `rag-search describe` (the CLI subcommand) bypasses `api.describe_collection` entirely, calling `descriptions.set_description`/`get_description` directly — it never runs the access check the MCP tool runs, and silently ignores its own inherited `--client` flag (accepted by argparse, never read). Contradicts `ARCHITECTURE.md`'s explicit claim that `api.describe_collection` is "the only writer, gated by the same `policy.resolve_scope` a search/grep request is." Not cross-client-exploitable (the CLI is inherently trusted), but a real documentation/behavior mismatch and a dead flag that misleads anyone auditing what a restricted client would see.
- **[MEDIUM]** `mcp-config --profile` validates against a narrower, hand-maintained profile list (`register.known_profiles()`) than the MCP adapter and `access.py` actually accept (any `valid_client_name` not reserved) — a user can run a new profile directly or grant it access rules, but can't get the convenience config snippet for it without hitting a spurious "unknown profile" error.
- **[MEDIUM]** No locking around the access.json/descriptions.json read-modify-write cycle — see priority finding #7.
- **[LOW/MEDIUM]** Three independent atomic-JSON-write implementations (`paths.write_json_atomic`, `policy.save_rules`, `descriptions.save_descriptions`) where one already-existing shared helper would do, plus `access._canonical`/`descriptions._canonical` are near-duplicate name-resolution functions that fold against inconsistent universes (the latter never consults `access.json`'s restricted-name list), which can let a restricted collection acquire a second, differently-cased description-store key instead of resolving to the same entry. Neither is a path-traversal issue (names are only ever compared as strings, never joined onto a filesystem path).
- **[MEDIUM]** `descriptions.py` has no cache analogous to `AccessStore`/`ConfigStore`, so `catalog.list_view` — called on every `rag_list_collections`, every CLI `list`, and every dashboard poll — reads and parses `descriptions.json` fresh every time.
- **[MEDIUM]** `service.py`'s `PASS_ENV` (which env vars reach a launchd-managed daemon) is a hand-maintained tuple that mirrors but doesn't derive from `spec.TUNABLES` — the exact pattern `ARCHITECTURE.md` says the dashboard's playground config endpoint deliberately avoids by deriving its flag list from the registry. A new tunable added to `spec.py` reaches an on-demand-spawned daemon (which inherits the whole environment) but silently fails to reach a `service install`-managed one, with nothing to catch the drift.
- **[MEDIUM]** The dashboard has no write path for collection descriptions (`ui/server.py`'s route table has an `access` entry but no `describe` entry) despite CLI and MCP both supporting it, and despite the module's own docstring describing the dashboard as exposing "exactly what the CLI can do" — feature-parity drift from the recent `rag_describe_collection` addition.
- **[LOW]** `view_as` ("act as this client") is honored for `search`/`grep` but hardcoded to `client="cli"` for indexing/admin actions in the dashboard — very likely intentional, worth a one-line comment to make that explicit.
- Clean on review: `paths.py`, `catalog.py`, `client.py`, `protocol.py`, `config.py`, the optional host module, `mcp/server.py`, `mcp/profiles.py` — centralized, consistent input validation; careful lock handling around daemon start/stop/cancel; the MCP adapter is a genuinely thin, fully-delegating layer with no duplicated access logic (confirmed by the existing `test_mcp.py` layering tests, which this review's findings don't contradict).

## How this interacts with the flexible-docs-location / export-import proposal

Several findings here directly affect the sequencing or design of the work already analyzed in `flexible-docs-location-analysis.md`:

- The planned collection-location registry (that doc's §1) is a new metadata store of exactly the kind implicated in findings #7/#8 above (no read-modify-write locking, no shared cache) — it should be built reusing a fixed version of `AccessStore`'s pattern, not adding a fifth bespoke store.
- The deleted-source cleanup gap (priority finding #8, detailed fully in the other doc's §1) is as much an "accuracy of indexing" finding for *this* review as it is a prerequisite for the multi-location proposal, and should be fixed once, not twice.
- Export/import's planned hard model-match gate (that doc's §3) should compare more than the bare model id, given finding "model identity is not reproducible" above (models.py) — at minimum record the resolved commit SHA in the export manifest even if the comparison itself stays id-based for v1.
- The case-folding bug in `policy.resolve_scope` (priority finding #1) should be fixed before multi-location ships, since multiple location roots materially raise the odds of case variation between a configured location's name and what a client requests.

## Top recommended actions (whole-codebase, ranked)

1. Fix `policy.resolve_scope`'s case-sensitive collection match (`policy.py:83-98`) — on the live search path, affects every surface.
2. Fix the same-stem single-file-indexing collision (`paths.py:316-323`, `worker.py:83-86`) — silent, undetected data loss.
3. Dedupe collection scope end-to-end to stop RRF double-counting (`search.py:269-270` and upstream).
4. Wire `Reranker` up to `RAG_SEARCH_RERANK_BATCH`/`RAG_SEARCH_RERANK_MAX_LEN` (`core/embedding.py:220-242`) — currently a no-op for the default backend.
5. Add offline-first model loading (`HF_HUB_OFFLINE`/`local_files_only` when cached) and route load-time failures through `model_tasks.explain_download_error` — directly serves this tool's own network-blocked deployment target.
6. Narrow `search_daemon.py`'s `_search_lock` to stop serializing the whole query pipeline across concurrent clients.
7. Add file locking around `access.json`/`descriptions.json` read-modify-write, and collapse the three atomic-JSON-write implementations onto one (`paths.write_json_atomic` plus an optional `mode`).
8. Ship the deleted-source cleanup fix from `flexible-docs-location-analysis.md` §1 (reclaim orphaned per-doc index/markup artifacts on ordinary `index new`, not just full `--wipe`).
9. Scope the legacy-torch-load safety patch (`core/embedding.py:114-140`) to the single trusted call instead of leaving it globally disabled for the rest of the process.
10. Route `rag-search describe` through `api.describe_collection` and add the dashboard's missing `/api/describe` route, so all three surfaces (CLI/MCP/UI) actually agree, matching what `ARCHITECTURE.md` already claims.
